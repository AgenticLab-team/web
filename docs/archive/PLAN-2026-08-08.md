# 第一部分：已实测的事实

## 1.1 服务器现状

> **这一节原本记着一份完整的主机画像**：ssh 登录名、云厂商、精确内核版本、
> 磁盘内存规格、frp 控制端口、防火墙当时是关的，以及家里那台跑 NekoBot 的机器的内网地址。
>
> 这个仓库要开源，而上面每一条都是**给攻击者省时间的东西** ——
> 尤其内核版本（直接对 CVE）和「防火墙关着」这两条。
> 站点现在躲在 Cloudflare 后面、源站只对 CF 网段开放，
> 而这套防护唯一的前提就是外面的人拼不出源站的样子。
>
> 具体的主机事实不写在仓库里。要查就上机器看，或者见被 gitignore 的 `.deploy-host`。

一台 Ubuntu LTS 的小云主机（2 核 / 4G 一档）。nginx 反代 + systemd 托管应用，
BBR 已开。Docker 没装 —— 这个站是单进程 + 一个 SQLite 文件，容器化只会多一层。

**NekoBot 不在这台机器上**，它跑在站长家里；两边靠 frp 打一条隧道，
上游 API 因此在服务器上表现为 `127.0.0.1:8090`。
**只映射了 API 端口，管理面板那个口没有映射** —— 隧道的两头都要当成攻击面看。

这条链路的脆弱点写在这里，因为它决定了一堆设计：
**家里的机器掉线 = 数据源断**。所以同步必须能降级、必须有健康监测，
而不是假设上游一直在。

## 1.2 NekoBot API（28 端点，已实测可用）

Base `http://127.0.0.1:8090/v1` · 鉴权 `X-API-Key: nk_xxx` · 文档 `/v1/docs`
Key（scopes `read`/`friends`/`send`，name=`jmr`）放 `.env` 的 `NEKOBOT_API_KEY`，**不入库不入仓**。

### 只读
| 端点 | 说明 |
|---|---|
| `GET /` | 接口自述 |
| `GET /whoami` | key 信息（name/prefix/scopes/calls） |
| `GET /stats/overview` | 全局概览 |
| `GET /conversations` | 会话列表 `?groups_only&bound_only&keyword&limit` |
| `GET /groups/{conv_id}/leaderboard` | 群发言榜 `?days&start_ms&end_ms&quality_min&limit&order` |
| `GET /groups/{conv_id}/activity` | 活跃度分布 `?days&by` |
| `GET /groups/{conv_id}/members` | 群成员 `?limit` |
| `GET /users/search` | 昵称找人 `?q*&limit` |
| `GET /users/{wx_id}/groups` | 此人在哪些群、各发多少 `?quality_min&days` |
| `GET /users/{wx_id}` | 用户画像 `?quality_min&samples` |
| `GET /messages` | 历史消息 `?conv_id&sender&sender_name&keyword&msg_type&days&start_ms&end_ms&min_len&include_self&order&limit&offset` |
| `GET /friend-requests` | 好友申请 `?pending_only&limit`（avatar_full 940x940、昵称、理由、wxid、申请人活跃度） |
| `GET /send/targets` `/send/stickers` `/send/quota` `/send/history` | 发送相关只读 |

### 写
`POST /friend-requests/{wx_id}/accept`
`POST /send/{text,image,file,voice,sticker,link,quote,pat,revoke}`
→ **本站只用 `accept` 和管理员公告用的 `send/text`。不做用户代发。**

### 核心概念
**高质量消息** = 长度 ≥ `quality_min`（默认 15）字的文本消息。
接口作者的设计意图：按总条数排名会让复读机上榜。
**→ 积分与排名一律以高质量消息为准，不用总条数。**

# 第二部分：产品定位

## 2.1 一句话

**给 Agentic Lab 社群一个"群聊之外的家"**：把签到兑换这类噪音搬离微信群，
把散落的群聊沉淀成可检索的知识资产，并给每个成员一个属于自己的空间。

## 2.2 设计判断（决定功能取舍）

**微信群的根本缺陷不是吵，是不沉淀。** 消息流走了就没了；好内容被刷掉；
新人进群看不到历史；上周的好链接找不回来。

→ 网站的**第一价值是检索与沉淀**，不是积分打卡。
→ 积分/连胜/等级是**留存钩子**，让人养成每天打开的习惯；但如果只有钩子没有肉，
   三周后必然死。两者缺一不可，但主次不能颠倒。

**第二价值是人脉发现。** AI Agent 社区里最稀缺的是"谁在做什么"。
636 个发言人散在 12 个群里，没人知道谁擅长什么。成员目录解决这个。

## 2.3 明确不做

| 不做 | 原因 |
|---|---|
| 网站代用户往群里发消息 | 你已明确否掉 |
| 站内即时聊天（IM） | 微信已经在做，重复建设且必然冷清 |
| 浏览用户不在的群 | 权限边界：只能看自己所在的群 |
| 公开索引群聊内容 | 半内部社区，登录可见即可 |

# 第三部分：身份与登录

## 3.1 首次绑定（双通道，解决加好友风控）

网站生成 **6 位验证码**（10 分钟有效，每人每日最多生成 3 次）：

**通道 A — 新人（不是机器人好友）**
1. 用户添加机器人为好友，在**申请理由**里填写这 6 位码
2. 服务端定时任务轮询 `GET /friend-requests?pending_only=true`
3. 理由中匹配到有效码 → 取该申请的 `wxid` 与 `avatar_full`
4. `POST /friend-requests/{wx_id}/accept` 自动通过
5. `GET /users/{wx_id}/groups` 校验其在 ≥1 个 bound 群 → 授予 `member`；否则标记 `external` 待审批

**通道 B — 老友（已是机器人好友，发不出申请）**
1. 用户**私聊机器人**发送这 6 位码
2. 服务端 `GET /messages?conv_id=<wxid>&keyword=<code>` 校验
3. 同样走群成员校验

> ⚠️ 通道 B 依赖"私聊消息可读"。`/conversations` 有 `groups_only` 参数，
> 说明非群会话在库里 —— 但**未实测**，动工时先验证。
> 若不可用，退化方案：管理员后台手动绑定 + 邀请码。

**双通道的意义**：绝大多数活跃老友走 B，不产生好友申请；只有真正的新人才加好友。
这直接缓解你担心的频繁加好友风控问题。

## 3.2 后续登录（不再依赖微信）

绑定成功后**强制引导**设置至少一种登录凭证：

1. **Passkey / WebAuthn**（首选，主推）— 指纹/面容/PIN，一键登录，无密码可泄露
2. **密码**（兜底）— Argon2id，强度校验，防撞库限流
3. **邮箱魔法链接**（可选）— 同时作为找回通道与通知渠道

安全策略：
- Passkey 可绑多个设备，后台可查看/命名/撤销
- 会话：短期 access token + 长期 refresh，设备列表可远程下线
- 敏感操作（改密码、解绑、删号）需二次验证
- 登录限流：IP + 账号双维度，失败递增退避
- 全程记录登录日志（时间/IP/UA/方式），用户自己可见

## 3.3 准入策略

| 类型 | 来源 | 权限 |
|---|---|---|
| `member` | 通过绑定 + 在 ≥1 bound 群 | 完整功能，可看自己所在群 |
| `external` | 管理员邀请码 / 申请后审批 | **看不到任何群消息**，仅论坛、活动、公开榜单 |
| `banned` | 管理员封禁 | 无 |

现阶段：**只有群成员能登录**。external 通道先建好数据模型和后台入口，默认关闭（feature flag）。

## 3.4 群成员身份的持续校验

人会退群。定时任务每日比对 `GET /groups/{conv_id}/members`：
- 用户退出某群 → 自动收回该群的消息可见权
- 退出所有群 → 降级为 `external`（保留账号和积分，不删数据），后台可见待处理列表

## 3.5 头像与昵称同步

- 绑定时抓一次（`avatar_full` 是 940x940 原图，做头像绰绰有余）
- 定时任务每日比对更新
- 用户可手动「立即同步」（限流：每小时 1 次）
- 允许用户设置**站内昵称**覆盖微信昵称（微信昵称仍作为身份标识展示在名片上）

# 第四部分：功能设计

## 4.1 首页 Dashboard

进站第一屏要在 3 秒内回答「我今天该做什么」和「群里发生了什么」。

- **今日卡片**：今日高质量消息数 / 打卡状态 / 连胜天数 / 距下一级还差多少分
  → 打卡按钮是首屏最显眼的主操作
- **群动态流**：我所在各群的最新精华消息（不是全量刷屏，是筛选后的）
- **本周榜单预览**：我的排名 + 上下各两名（制造追赶感）
- **未读**：@我的、我的帖子被回复、活动提醒
- **社区脉搏**：今日总消息数、活跃人数、新成员

## 4.2 群聊检索与沉淀 ★核心

权限：**只能访问自己所在的群**（服务端强制校验，不是前端隐藏）。

- **全文搜索**：跨群 / 按人 / 按时间范围 / 按消息类型 / 最小长度
  → 微信搜索烂到没法用，这里做好就是杀手锏
- **时间机器**：选任意一天，回看某群当天完整记录
- **每日/每周精华**：自动挑选高质量消息（长度 + 被回复密度 + 含链接/代码）
  → 新人进群补课、老人回顾，都靠这个
- **链接资源库**：自动抽取群里发过的所有链接，去重、抓标题、按群/时间/发布人归档
  → AI Agent 社区的刚需。半年群聊里的好资源本来全埋了
- **我的存档**：搜索我自己说过的所有话（"我上次发的那个 repo 在哪个群来着"）
- **关键词订阅**：订阅关键词（如 "MCP"、"Claude"），群里有人提到时站内通知
  → 这个功能会让人主动打开网站

## 4.3 排行榜

主排序恒为**高质量消息数**。维度：

- 范围：单群 / 全站
- 周期：日榜 / 周榜 / 月榜 / 总榜
- 榜单类型（做多个，避免单一维度让人绝望）：
  | 榜 | 指标 |
  |---|---|
  | 贡献榜 | 高质量消息数（主榜） |
  | 深度榜 | 平均消息长度 |
  | 连胜榜 | 连续打卡天数 |
  | 夜猫子 / 早鸟 | 按 `activity?by=hour` 分布 |
  | 破冰榜 | 回应新人最多 |
  | 新星榜 | 近 30 天加入者中的贡献第一 |
- 每项都显示**排名变化箭头**（↑3 / ↓1），这是追赶动机的来源
- 榜单可分享成图片卡片

## 4.4 打卡 · 积分 · 等级 · 连胜

**打卡规则**：当日在任一群产出 ≥3 条高质量消息，才能在网站打卡。
（先有贡献再打卡，避免纯签到党；数值后台可配）

**积分表**（全部后台可配，不硬编码）

| 行为 | 积分 |
|---|---|
| 达标打卡 | +10 |
| 每多 5 条高质量消息 | +5（当日封顶 +20） |
| 连胜第 N 天 | +min(N, 30) |
| 发帖被加精 | +50 |
| 发帖 | +5（每日封顶 2 次） |
| 回帖被点赞 | +2（每日封顶 +20） |
| 活动签到 | +20 |
| 邀请新成员绑定 | +30 |
| 首次完善名片（技能标签） | +20（一次性） |

**连胜**：断签清零。可用积分买「补签卡」（200 分，每月限 1 次）。
连胜里程碑（7/30/100/365 天）给徽章。

**等级**：L1–L10，累计积分开档，等级解锁权限：
- L2 发帖 · L3 创建话题 · L4 活动优先报名 · L5 专属头像框
- L6 关键词订阅上限提升 · L8 版主候选资格 · L10 名人堂

**反作弊**（必须做，否则积分体系一周就废）：
- 只认 `quality_min` 以上的**文本**消息
- 同一分钟内多条按 1 条计
- 重复/近似内容不计（简单相似度去重）
- 纯链接、纯表情、纯转发不计
- **所有积分由服务端定时任务从 API 拉取核对后发放，前端只是展示**
- 异常增长进后台风控队列人工复核

## 4.5 论坛

- 版块（可后台增删）、发帖、回复、点赞、收藏、@提及
- Markdown + 代码高亮（AI Agent 社区必需）+ 图片上传

- **★ 群聊一键成帖**：把群里的一段对话（选中若干条消息）转成帖子沉淀下来。
  这是群与论坛的桥梁，也是这个论坛区别于任何普通论坛的地方。
  权限：本人的消息自己可转；他人消息需管理员操作或作者同意。
- 举报 → 审核队列

## 4.6 活动

- 发布活动：标题、封面、时间、地点/线上链接、名额、报名门槛（等级/积分/所在群）
- 报名 / 候补队列 / 取消
- **签到码**：活动现场出示，扫码或输码签到 → 发积分
- 活动回顾：照片、纪要、可关联论坛帖
- 提醒：开始前站内 + 邮件通知

## 4.7 积分商店

积分兑换（库存与上架后台管理）：
- 社区邀请码 · 活动优先报名权 · 补签卡 · 专属头像框/徽章
- 实物周边（需填收货信息 → 走订单流程，后台发货标记）
- 兑换记录、订单状态

## 4.8 成员目录（人脉发现）

- 成员卡片：头像、站内昵称、微信昵称、等级、徽章、所在群、技能标签、一句话简介
- 按**技能标签**筛选（自填 + 后台维护标签库）：RAG / Agent / 微调 / 多模态 / 前端…
- 「谁在做 X」搜索
- 个人主页：贡献曲线、活跃时段热力图、精华发言、论坛帖子
- 隐私开关：可选择不出现在目录中

## 4.9 通知

站内信 + 邮件（可分别开关）：
- @我了 / 帖子被回复 / 帖子被加精
- 关键词订阅命中
- 连胜即将中断（当日 21:00 未达标时提醒）★ 这条对留存最有效
- 活动提醒 / 报名成功 / 候补转正
- 等级提升 / 徽章获得
- 管理通知（警告、封禁、申诉结果）

# 第五部分：管理后台（重点）

原则：**后台不是"加个 admin 页面"，是完整的第二套产品。** 所有写操作留痕，
所有数值可配，危险操作有闸门。

## 5.1 角色与权限（RBAC + Scope）

| 角色 | 范围 | 能力 |
|---|---|---|
| `owner` | 全站 | 一切；唯一可授予/撤销 admin；可改系统设置 |
| `admin` | 全站 | 用户、内容、活动、积分、公告；**不能**改 owner、不能改系统级配置 |
| `moderator` | 指定版块 | 该版块内容审核（删/锁/精/置顶） |
| `group_admin` | 指定群 | 该群成员管理、榜单、群相关公告 |
| `auditor` | 全站只读 | 查看所有数据与审计日志，**零写权限** |
| `member` | 自己 | 普通用户 |
| `external` | 受限 | 无群消息访问权 |
| `banned` | — | 禁止登录 |

实现要点：**权限点（permission）粒度化**，不要写 `if (role === 'admin')`。
形如 `forum.post.delete`、`user.points.adjust`、`group.messages.read:<conv_id>`。
角色 = 权限点集合，可后台自定义组合。

## 5.2 后台模块

## 架构原则

1. **NekoBot API 是上游只读数据源**，本站库存业务数据（身份、积分、论坛、活动）
2. **API key 只在服务端**，绝不下发前端
3. **上游数据本地物化**：消息按天聚合入库，全文索引本地建
   → frp 隧道抖动时站点仍可用（降级为"数据更新至 X 时"），不白屏
4. **权限在服务端强制**：群消息访问权每次查询都校验，不靠前端隐藏
5. **积分只由服务端定时任务发放**，前端不可触发
6. **所有管理写操作进审计日志**

## 7.3 存储与缓存策略（磁盘受限下的设计）

### 先算账，再定策略

实测：45,340 条 / 51 天 ≈ **890 条/天**。一条中文消息含元数据约 300 字节。

| 项目 | 一年体量 |
|---|---|
| 消息正文 + 元数据 | 32.5 万条 × 300B ≈ **100 MB** |
| FTS5 索引（约 2×） | ≈ **200 MB** |
| 每日聚合统计 | 636 人 × 12 群 × 365 天，稀疏后 ≈ **20 MB** |
| 头像（256px webp，636 人） | ≈ **20 MB** |
| 业务数据（论坛/积分/活动/日志） | ≈ **100 MB** |
| **文本侧合计** | **≈ 450 MB / 年** |

**结论：文本不是问题**（52 GB 可用）。真正吃盘的是**媒体**：
一个群一天 50 张图 × 500 KB = 25 MB/天 = **9 GB/年**，12 个群就能撑爆。

### 三条铁律

**① 媒体永不落盘原图**
- 图片/文件/语音**不下载存储**，只存元信息（类型、大小、上游引用、发送人、时间）
- 需要展示时走**服务端代理**（key 不能下发前端）+ 磁盘 LRU 缓存
- LRU 缓存**硬上限 2 GB**，超出按最近最少使用淘汰，后台可调
- 只持久化**缩略图**：webp、长边 ≤ 320px、≈ 15 KB
- 头像：webp 256px（`avatar_full` 是 940×940 原图，压缩后 ≈ 30 KB）

**② 文本分层保留（本地是缓存，不是唯一副本）**

关键认知：**上游 NekoBot 才是数据源**，本地库是加速层。冷数据可放心裁剪，需要时回源。

| 层 | 范围 | 保留内容 |
|---|---|---|
| 热 | 近 90 天 | 全量正文 + 全量 FTS 索引 |
| 温 | 90 天 – 1 年 | 全量正文；FTS 索引**仅高质量消息** |
| 冷 | > 1 年 | 仅保留高质量消息正文 + 每日聚合统计；其余按月 gzip 归档或丢弃 |

各层天数、是否归档、归档路径 —— **全部后台可配**，不写死。

**③ 水位监控 + 自动泄压**
- 后台仪表盘常驻显示磁盘水位、各表体积、媒体缓存占用
- 阈值告警（默认 70% 提醒 / 85% 自动触发裁剪 / 92% 停止媒体缓存写入）
- 裁剪任务可手动触发，执行前显示"将释放约 X MB"预览
- 每次自动裁剪记入审计日志

### 为什么改用 SQLite

原方案写的是 PostgreSQL，改掉。理由：
- 数据量级（一年几百 MB）SQLite 完全吃得下，FTS5 中文分词配 `simple`/`icu` 够用
- 3.6 G 内存下少一个常驻进程，省内存也省盘
- 备份 = 复制一个文件，配合 `VACUUM` 和 WAL，运维成本几乎为零
- 升级路径：真到了 SQLite 扛不住的规模（>500 万条消息），Drizzle 换 PG 驱动即可

# 第九部分：需要提醒的两件事

**1. 可检索性会改变群聊的性质。**
你的决定是"微信里能看到的这里也能看到"，这没问题。但要意识到：微信里翻半年前的记录
几乎不可能，网站上一搜就出来 —— 同样的数据，可达性完全不同。
建议：上线前在群公告里明说"群聊记录已同步到社区站，成员可检索自己所在群的历史"。
不是征求同意，是知情。这能避免以后有人翻旧账时的尴尬。

**2. frp 隧道是单点。**
家里那台机器掉线，整个数据源就断了。所以本地物化不是优化，是**必需**。
同时后台要有隧道健康监控和告警。
