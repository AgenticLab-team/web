# SMTP 收信网关

> 一个**独立的进程**，不是站点的一部分。设计理由见仓库根目录的 `MAIL.md` 第五节。

## 它和站点之间只有一条线

网关不连数据库、不 import 站点的任何代码、不共享进程。
两者之间只有三个 HTTP 调用，全部签名、全部带协议版本号：

| 调用 | 方向 | 干什么 |
|---|---|---|
| `GET /api/mail/routes` | 网关 → 站点 | 每分钟拉一次「哪些域名收信」 |
| `GET /api/mail/routes?address=` | 网关 → 站点 | RCPT 时现查具体地址（缓存 30 秒） |
| `POST /api/mail/inbound` | 网关 → 站点 | 投递一封信（HMAC 签整个请求体） |

拆开的代价是多一个服务要维护，买到的是**部署拓扑可以随时改**。

## 两种拓扑

### ① 同机（现在这样）

```
       ┌──────────────────── 一台服务器 ────────────────────┐
25 ───▶│ 网关进程  ──http://127.0.0.1:3000──▶  Next 站点     │
       └──────────────────────────────────────────────────┘
```

投递是一次**本地回环**：不走 nginx、不走 Cloudflare，快且少一层会挂的东西。

⚠ **代价：MX 记录会把源站 IP 公开出去。**
站点现在躲在 Cloudflare 后面、源站只对 CF 网段开 80/443，
而**这套防护的前提就是没人知道源站在哪**（`DEPLOY.md`）。
MX 是公开记录，Cloudflare 又不代理 SMTP —— 一旦 MX 指过来，
一百个域名的 DNS 里就都写着源站的地址了。

这是**有意接受的代价**，不是疏忽。想收回来就切到②。

### ② 分机（以后）

```
25 ───▶ 网关机（独立 IP） ──https──▶ Cloudflare ──▶ 源站
```

`SITE_URL` 改成 `https://agenticlab.sh`，MX 改指网关机。
源站 IP 重新藏起来，网关机上没有数据库、没有代码仓库、没有任何值得拿的东西。

### ③ 多机（更以后）

网关**不存任何状态**（路由表是缓存，地址查询是缓存），
所以加一台就是再跑一个进程：MX 加一条低优先级记录即可。

**从①到③不用改一行代码**，只改环境变量和 DNS。这是拆开的全部意义。

## 装

```bash
# 同机
MAIL_INGRESS_SECRET=<和站点那个一模一样> \
SITE_URL=http://127.0.0.1:3000 \
bash install.sh

# 分机
MAIL_INGRESS_SECRET=... SITE_URL=https://agenticlab.sh bash install.sh
```

脚本幂等，可以反复跑。密钥生成：

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

⚠ **两边必须一模一样。** 站点那边不配的话，收信接口直接返回 503 关门 ——
这是有意的：放行的话任何人都能往任意地址投递任意内容，
而它看起来完全正常在工作。

网关跑在**专用账号 `mailgw`** 下，不是站点那个账号：
它是唯一一个直接暴露在公网上的进程（25 端口对全世界开着），
被打穿的时候不该顺手拿到数据库。

### 顺带一个实测过的约束

**源站那台机器出站 25 端口被云厂商封死**（连 gmail 的 MX 直接超时）。
也就是说它连退信都发不出去 —— 将来要发信只能走 HTTPS 接口
（Cloudflare Email Sending / Resend 之类），无论网关在哪台机器上。

## 升级时的顺序

网关和站点是分开部署的，所以**版本会有一段不一致的时间**。
协议里有个版本号（网关 `PROTOCOL` ↔ 站点 `src/lib/mail/protocol.ts`），
一条测试盯着两边对得上。

规矩：**先升站点，再升网关。**
站点向后兼容一格（`MAIL_PROTOCOL_MIN`），所以老网关在这中间照常投递。
反过来的话，新网关会发站点不认识的版本，站点回 400，
网关把它当永久失败 —— 那一段时间的信就真的没了。

### 证书

同机部署时源站上已经有 nginx 和 certbot，加一个域名即可；
分机时用 standalone 模式（那台机器上没有 nginx）：

```bash
sudo certbot certonly --standalone -d mx.agenticlab.sh
```

签好之后把路径写进 `.env` 的 `TLS_KEY_PATH` / `TLS_CERT_PATH`，
并让 `mailgw` 读得到（`setfacl` 或者把证书拷一份过去）。

不配证书**也能跑**，但每一封信在路上都是明文的，而且没有任何地方会显示这件事 ——
启动日志里会吵一句，仅此而已。

## DNS

**完整的一步步操作见 [DNS.md](DNS.md)** —— 100 个域名里 89 个要配、
**11 个一条记录都不能配**，还有两件配错之后要重来一百遍的事。

摘要：

| 在哪 | 记录 | 值 |
|---|---|---|
| Cloudflare | `A mx` | 服务器 IP，**必须灰云** |
| DNSPod ×89 | `MX @` | `10 mx.agenticlab.sh` |
| DNSPod ×89 | `TXT @` | `v=spf1 -all` |
| DNSPod ×89 | `TXT _dmarc` | `v=DMARC1; p=reject;` |

⚠️ **灰云那一条最容易栽**：橙云会让 Cloudflare 代理这个名字，
而 CF 不代理 SMTP —— 邮件直接收不到，
但 `dig` 查出来一切正常（返回的是 CF 的 IP）。

## 它做什么、不做什么

**做**：

- RCPT 阶段查地址，不认识的**当场拒**（550）
- 域名快照每分钟刷一次；具体地址现问站点（缓存 30 秒，正负都缓存）
- 大小限制、每 IP 连接频率限制
- 解析 MIME，把结构化结果经 HTTPS + HMAC 推给站点

**不做**：

- **不发信，也不中继**（`AUTH` 整个禁掉）
- **不做内容反垃圾**。在 SMTP 会话里做重活会拖垮整个监听 ——
  真要做的话在这台机器上装 rspamd，让它在前面挡一层

## 几个判断，写下来免得以后被人「顺手改掉」

**不认识的地址在 RCPT 阶段拒，不能收下来再退信。**
垃圾邮件的发件人几乎都是伪造的 —— 我们退回去的每一封都砸在一个无辜的邮箱上。
这也是被列进黑名单最快的一条路。

**路由表拉不到时，继续用手上那份旧的，不清空。**
清空的话，站点一次几分钟的重启会让网关在这期间拒收所有的信，
而那些信大多不会重投第二次。一份旧名单最坏的后果是收下一封本该拒的信，
那比拒掉一批本该收的信轻得多。

**单地址查不到时收下，不拒。**
站点短暂不可用不是发信人的错，而拒信是不可撤销的：
对方收到「此地址不存在」之后不会再试。收下来最坏是落地时被判成 rejected，
而那一层有完整的留痕，事后查得到。

**推不上去回 451（临时失败），不回 5xx。**
回 5xx 这封信就永远没了，而问题多半在我们这边。
站点对同一个 Message-ID 有去重，重投不会存两份。

## 查问题

```bash
sudo journalctl -u agenticlab-mail -f
# 从外面试一封
swaks --to test@rickroll.icu --server mx.agenticlab.sh
```

收不到信时的排查顺序：

1. `dig MX 那个域名` —— 十次有九次是这一条没配好
2. 网关日志有没有这次连接
3. 站点后台 `/admin/mail` 的「被拒的投递」—— **拒掉的也留痕**，
   「我朋友说发了我没收到」这句话就是靠这张表回答的
